### Lessons learned during implementation

Constraints discovered while building M1-M3, recorded so the next iterations
do not re-step on the same rakes:

- **DSL `action` / `guard` accept only remote captures, not inline closures.**
  `Macro.escape/1` cannot serialise an anonymous `fn -> end` closure into the
  AST emitted by `__before_compile__`. Always write `&MyMod.fun/1` (or
  `&__MODULE__.fun/1` from inside the statechart module). Inline `fn` is
  rejected at compile time with a clear error from `:elixir_quote`.
- **`on_entry/1` and `on_exit/1` macros collide with `ExUnit.Callbacks` inside
  test modules.** Fixture statecharts that use `on_exit` MUST be defined as
  separate top-level modules in the test file (not nested inside the
  `defmodule SomeTest do use ExUnit.Case end` block), because nested defmodules
  inherit macro imports from the surrounding module. Pattern in
  `test/ex_machine/integration/hierarchical_test.exs`.
- **`Configuration.atomic_states/2` includes both `:atomic` and `:final` nodes.**
  A final node is a leaf for all practical purposes — it terminates a region.
  Treat them uniformly when querying active leaves.
- **`mix.exs` version is single-source via `@version` module attribute.**
  Don't duplicate the literal in `docs/source_ref` or anywhere else; reference
  `@version`. The 0.1.x line had a known bug with two version literals out of
  sync.
- **Credo strict is enabled but `AliasUsage` is loosened to
  `if_called_more_often_than: 30`.** Macro modules legitimately use fully
  qualified names because aliases inside `quote` blocks would leak to user
  modules. Keep this exception when adding more meta-programming code.
- **Engine M3 raises explicitly for `:history`/`:choice` transition targets
  and for `type: :internal`.** The DSL accepts and validates them at compile
  time so user code can already declare them, but the engine refuses to
  execute. M4 lifts both restrictions.
- **M4 — internal transitions degrade gracefully.** SCXML defines
  `:internal` semantics only when the source is a composite AND the target
  is one of its proper descendants. Outside that case the transition behaves
  as `:external`. The engine encodes this by overriding the LCCA to
  `source` only in the qualifying case; everything else flows through the
  external path unchanged.
- **M4 — choice resolution is recursive and happens before LCCA.** The
  resolved (non-pseudostate) target drives all set computation, so a
  `cond_branch` may target another `:choice` and the engine follows the
  chain until it lands on a real state. Guards see the *pre-exit* context
  to keep the choice deterministic relative to the dispatched event.
- **M4 — history is recorded *during* the microstep that exits the
  composite, not lazily.** The snapshot is taken from the configuration
  *before* `Configuration.exit/2` runs, since after that point the
  composite's children are no longer in the set. Restoration on the entry
  side reads from `machine.histories` (a `%{hist_id => MapSet.t/0}` map)
  and falls back to `history_default || parent.initial` when no snapshot
  exists.
- **M5 — a microstep applies a *set* of transitions, not one.** The engine
  picks at most one transition per active atomic state (climbing the
  ancestor chain) and reduces the result with `remove_conflicting/2`.
  Transitions conflict when their exit sets overlap; the deeper-source
  one wins, otherwise document order (atomic-state ordering) breaks the
  tie. The combined exit chain is sorted globally deepest-first, while
  combined entry chains are concatenated in selection order — non-
  conflicting transitions across regions have disjoint sub-trees so
  parent-first is preserved without re-sorting.
- **M5 — done events bubble up.** When a region reaches its `:final`,
  `done.state.<region>` is raised. If that completes every sibling region
  of the enclosing parallel, `done.state.<parallel>` is raised in turn,
  and the walk continues until the chain hits an ancestor whose other
  children are still in flight (or the root). The machine's `:running?`
  flag is decided by `stopped?/2`, which checks both compound and
  parallel terminal configurations of the root.
- **M5 — `Trace.Microstep` field rename.** `:transition` (single) became
  `:transitions` (list) so traces can record multi-region steps. There is
  no migration path; v0.1 is gone.
- **M6 — server stays alive after the machine stops.** Reaching a
  terminal configuration sets `Snapshot.running? = false` but does NOT
  terminate the GenServer: `send_event/2` becomes a silent drop and
  `call_event/2` returns `{:error, :not_running}`. This lets subscribers
  query the final snapshot. Use `stop/1` to terminate explicitly.
- **M6 — pub/sub uses `Registry` keys: :duplicate, dedup at dispatch.**
  `subscribe/1` always succeeds (even called twice); the `broadcast/2`
  helper `Enum.uniq`s the recipient pids before `send/2`. Trade-off:
  `unsubscribe/1` removes ALL of the calling process's registrations
  for a given server — fine since the public API offers no way to make
  multi-context registrations distinguishable.
- **M6 — telemetry only fires from the server, never from the engine.**
  Pure-mode callers of `ExMachine.dispatch/2` get zero telemetry by
  design: the engine must remain free of side effects so it stays
  trivially testable. Servers wrap each dispatch in a
  `:telemetry.span/3` (`[:ex_machine, :macrostep]`) and emit
  `[:ex_machine, :transition]` and `[:ex_machine, :stopped]` from
  `ExMachine.Telemetry`.
- **M6 — `mix.exs` now has `mod: {ExMachine.Application, []}`.** The
  application supervisor brings up `Registry` (`name: ExMachine.PubSub`).
  Library users do not need to add anything to their own application
  tree to use `ExMachine.Server`.
- **M7 — engine surfaces side-effect requests on `%Machine{}` instead of
  acting on them.** `step.delayed`, `step.invokes`, `step.cancels` are
  accumulated into `machine.pending_delayed | pending_invokes |
  pending_cancels`, reset at the start of every `dispatch/2`. Pure
  callers can introspect them; the server consumes them. The engine
  itself remains side-effect-free.
- **M7 — invoke uses a user-chosen atom id, not an opaque ref.** Each
  invocation produces `done.invoke.<id>` / `error.invoke.<id>` events,
  so the DSL must be able to pattern-match the event name at compile
  time. `Step.invoke/4` therefore takes an explicit `id` (atom). The
  internal task ref is opaque and used only to correlate the
  `{ref, result}` and `{:DOWN, ref, ...}` messages to the invocation.
- **M7 — auto-cancellation reads `machine.trace.exited`.** After every
  macrostep the server walks the trace's exit set and kills any timer
  or invocation whose owner state was exited. This is the *only* place
  where the server uses the trace — choosing trace as the carrier
  avoided adding a separate "states exited this macrostep" field on
  `%Machine{}`.
- **M7 — `Process.flag(:trap_exit, true)` is set on the server.**
  Otherwise a brutal-killed invocation task could trigger an EXIT that
  also takes down the server. With trap on, `{:EXIT, ...}` lands in
  `handle_info(_, state)` which silently ignores it. Side benefit: a
  crashing user-supplied invoke does not crash the server.
- **M7 — `terminate/2` cancels all pending timers.** `Process.send_after`
  schedules messages that survive the GenServer process. Cancelling
  them on terminate keeps the host BEAM clean for tests that spin
  servers up and down rapidly.
- **M8 — visualisation reads `%Definition{}` only.** No engine, no
  server, no side effects, safe at compile time. Two backends:
  Mermaid `stateDiagram-v2` (paste into mermaid.live) and W3C SCXML
  XML. Choice pseudostates have no SCXML equivalent and are emitted
  as a comment; the user is expected to translate them to guarded
  transitions by hand.
- **M8 — Mermaid transition rendering happens at the parent scope, not
  inside the source's block.** A compound's outgoing transition
  `Source --> Target` is a sibling of the compound's own
  `state Source { ... }` declaration, because Mermaid would otherwise
  treat `Source` as a state INSIDE itself. Implementation: each
  `child_section/3` emits the child's *declaration* (block / pseudostate
  marker / nothing) followed immediately by the child's *transitions*,
  both at the parent's indent level.
- **M8 — final states are not declared, only used as `[*]` arrow
  targets in Mermaid.** Mermaid stateDiagram-v2 has no `<<final>>`
  marker; the convention is to point at the parent's terminator with
  `Source --> [*]`. SCXML, on the other hand, uses an explicit
  `<final id="..."/>` element.

## Context (original brief)

ExMachine è un'implementazione funzionale di Statechart in Elixir, scritta nel
2018 e ripubblicata cosmeticamente nel 2025. Il core era solido ma incompleto:
`ServerMachine` placeholder, history per metà, niente regioni ortogonali,
niente choice pseudostates, niente distinzione internal/external. Validazione
duplicati commentata. Le scelte (`:exm_queue` e `:exm_params` iniettati nel
context utente) inquinavano il dominio del chiamante.

Il progetto non ha utenti in produzione. L'utente lo userà internamente in
altri suoi software e vuole rilasciarlo come libreria seria (Hex). Quindi:
**niente vincoli di retrocompatibilità**, ripartenza pulita verso una `0.2.0`
genuinamente al livello SCXML/XState, con DSL macro pura, engine
SCXML-conforme, server-mode con delayed events e invoked services, telemetry,
visualizzazione, e una suite di test seria (unit + integration + property +
SCXML conformance).

## Goals

1. **API moderna**: DSL macro come unico modo di definire macchine,
   validazione completa a compile-time.
2. **Engine SCXML-conforme**: configurazione come set, run-to-completion,
   history (shallow+deep), choice, internal/external, parallel regions.
3. **Server-mode credibile**: `ExMachine.Server` con send/call eventi,
   delayed events, invoked services, telemetry events.
4. **Osservabilità**: telemetry + handler Logger attachable, export
   Mermaid/SCXML.
5. **Qualità**: doctest, unit test, integration test, property test
   (StreamData), porting selettivo della SCXML conformance suite.
   Coverage > 90% sul core.
6. **Toolchain attuale**: Elixir 1.18 / OTP 26 minimum (matrix CI 1.16-1.18 ×
   OTP 26-27), dialyzer + credo + formatter puliti.

## Architectural decisions

### 1. DSL macro pura (sostituisce le struct legacy)

Definizione utente:

```elixir
defmodule TrafficLight do
  use ExMachine.Statechart

  initial_context %{cycles: 0}
  initial :red

  state :red do
    on_entry &__MODULE__.log_red/1
    on :timer, target: :green
  end

  state :green do
    on :timer, target: :yellow
  end

  state :yellow do
    on :timer, target: :red, action: &__MODULE__.incr/1
  end

  def log_red(step), do: step
  def incr(step), do: ExMachine.Step.update(step, :cycles, &(&1 + 1))
end
```

Sotto il cofano: la DSL accumula attributi via `Module.register_attribute/3`,
`__before_compile__` compila in `%ExMachine.Definition{}`, genera
`__statechart__/0` con la definizione validata. Macro disponibili:
`state`, `parallel`, `region`, `history`, `choice` (`cond_branch` /
`otherwise`), `final`, `on_entry`, `on_exit`, `on`, `initial`,
`initial_context`. Validazione compile-time: nomi univoci, target esistenti,
initial valido, parallel con almeno 2 regioni, history solo dentro composite,
choice con almeno una branch.

### 2. Configurazione come `MapSet`

Status quo legacy: `[["s11", "s1", "root"]]` (lista di catene). Limite: non
rappresenta config parallel.

Nuovo: `configuration :: MapSet.t(state_id)` contenente tutti gli ID attivi.
Le query si fanno sull'oggetto `Definition` compilato. Modello SCXML
standard, abilita le regioni ortogonali.

### 3. Separazione context utente / run-state

Status quo legacy: `:exm_queue` e `:exm_params` iniettati nella mappa context
dell'utente. Brutto, fragile.

Nuovo: actions e guards ricevono `%ExMachine.Step{}`:

```elixir
%ExMachine.Step{
  context: term,        # solo dato utente, mai inquinato
  event: term | nil,    # evento corrente
  raised: [event],
  delayed: [{ref, event, ms, owner_state}],
  invokes: [{ref, spec, owner_state}],
  cancels: [ref]
}
```

Helper: `Step.assign/3`, `Step.update/3`, `Step.raise_event/2`,
`Step.send_after/4`, `Step.invoke/3`.

### 4. Engine SCXML-aligned

Pipeline pubblica (`ExMachine.Engine`):

```
init/1   → enter_states(initial_set) → run_to_completion
dispatch → select_transitions(event) → microstep → run_to_completion
run_to_completion → loop:
                        select_eventless_transitions → microstep
                        oppure drain queue interna → microstep
                        finché stable
```

Funzioni private modellate sul SCXML W3C algorithm: `select_transitions/2`,
`select_eventless/1`, `compute_exit_set/2`, `compute_entry_set/3`,
`microstep/4`, `run_to_completion/1`, `lcca_external/3`. Per parallel +
history (M5) servirà anche `remove_conflicting_transitions/2`.

Ogni macrostep produce un `%ExMachine.Trace{}` con microsteps (oldest-first),
transizioni, stati entered/exited.

### 5. History, choice, internal/external, done events

- **History**: `histories: %{composite_id => MapSet.t}` salvata in exit.
  Pseudostato come target, risolto in `compute_entry_set/3` (deep restituisce
  sub-config completa, shallow solo i figli diretti).
- **Choice**: pseudostato con `[{guard, target}, ..., {nil, target}]`.
  Risolto durante `compute_entry_set`, ricorsivo (choice→choice ammesso,
  fallback su `otherwise`).
- **Internal transitions**: flag `:type` su `Transition`, l'engine non
  aggiunge il source all'exit-set se il target è descendant del source.
- **Done events**: `done.state.<id>` (atom) emesso quando un compound
  raggiunge il suo final, e quando tutte le regioni di un parallel
  raggiungono final. `Engine.done_event/1` è la funzione utility che
  produce l'atom.

### 6. Server-mode (`ExMachine.Server`)

GenServer wrapper con `use ExMachine.Server, statechart: MyMachine`. API:

```elixir
{:ok, pid} = MyMachine.start_link(context: %{}, name: :tl)
MyMachine.send_event(:tl, :timer)               # cast
{:ok, snap} = MyMachine.call_event(:tl, :timer) # call sincrono
MyMachine.get_configuration(:tl)
MyMachine.get_context(:tl)
MyMachine.subscribe(:tl)                        # via Registry built-in
MyMachine.stop(:tl)
```

- **Delayed events**: `Step.send_after/4` registra `{ref, event, ms,
  owner_state}`. Server schedula `Process.send_after`, tiene mappa
  `{ref, owner_state}`. All'exit dello state proprietario, timer non
  scaduti vengono cancellati.
- **Invoked services**: `Step.invoke/3`. Server usa `Task.Supervisor`
  (linkato, strategia `:transient`). `done.invoke.<id>` su success,
  `error.invoke.<id>` su failure. Su exit dello state che ha invocato →
  `Task.shutdown`.
- **Subscribe**: built-in via `Registry`. Eventi pubblicati:
  `{:ex_machine, :transition, %Snapshot{}}`, `{:ex_machine, :stopped, reason}`.

### 7. Telemetry

Eventi standard:

```
[:ex_machine, :macrostep, :start | :stop | :exception]
[:ex_machine, :microstep]
[:ex_machine, :transition]
[:ex_machine, :state, :enter | :exit]
[:ex_machine, :action, :exception]
[:ex_machine, :guard, :exception]
```

`ExMachine.Logger.attach(level: :debug)` per logging strutturato.

### 8. Visualization

- `ExMachine.Visualize.to_mermaid/2` → stringa per `stateDiagram-v2`
  (priorità 1, semplice, target `mermaid.live`).
- `ExMachine.Visualize.to_scxml/2` → XML SCXML W3C-conforme (priorità 2,
  target tool tipo `statechart.io`).

### 9. Toolchain

- Elixir `~> 1.16` (test matrix 1.16, 1.17, 1.18), OTP 26 e 27.
- Deps: `:telemetry ~> 1.2` (runtime), `:stream_data ~> 1.1` (test),
  `:credo ~> 1.7` (dev/test), `:excoveralls ~> 0.18` (test), `:ex_doc`,
  `:dialyxir`.
- `mix.exs` versione single-source via `@version` module attribute.
- Hex package: solo `lib/`, `mix.exs`, `README*`, `CHANGELOG*`, `LICENSE*`.

## Risks and mitigations

| Risk | Mitigation |
|------|------------|
| Algoritmo SCXML parallel + history + choice complesso | Implementare per tasselli (M3 → M4 → M5), ogni feature dietro test SCXML conformance specifici. Non passare a M5 finché M4 non è verde. |
| DSL compile-time troppo magica o limitante | Esporre `Definition.build!/1` come API "definition struct" documentata per casi avanzati / generazione programmatica. |
| `Step` complica le actions semplici | Sezione dedicata in `guides/actions_and_guards.md` con esempi. |
